# Hookline workplan

Hookline helps developers turn a webhook that broke their handler into a test they can run again. The first users are backend and integration developers who already receive events locally through a provider CLI, a tunnel, or a test sender. The TUI is for exploring real captures. A small command-line replay path can make reviewed fixtures useful in local development and CI.

GitHub is the first distribution channel. Follow the release checklist in order, then use the pilot to choose the next investment. Check off each item when its completion criterion is met. Conditional sections apply when the pilot supports that work.

## 1. Make replay trustworthy

- [x] **Fix Stripe signing.** Use the full `whsec_…` string as the HMAC key in `internal/sign/sign.go`. Done when a test vector generated by Stripe’s SDK matches Hookline’s output and the test that expects base64 decoding has been replaced. [Stripe Go verifier](https://raw.githubusercontent.com/stripe/stripe-go/v82.5.1/webhook/client.go#L45)
- [x] **Reject partial captures in replay.** Check `Truncated` in the shared replay path. Done when tests show that listener-truncated and store-truncated deliveries produce an actionable error before any request is sent.
- [x] **Preserve truncation during editing.** Keep the original capture’s truncation flag on edited copies. Done when the warning stays visible and diff review cannot bypass the replay check.
- [x] **Mark partial cURL exports.** Make partial captures produce an explicit explanation in place of a ready-to-run export. Done when copying a truncated capture cannot present it as a complete request.
- [x] **Bind remote replay confirmation to one send.** Show the destination and request, retain the edited body until the user chooses, and invalidate confirmation on cancel or a change of request or target. Done when tests show that cancel sends zero requests and confirmation sends the exact reviewed body once.
- [x] **Report failed history writes.** Surface failures from `Store.Append` in the TUI and distinguish them from live UI queue drops. Done when an injected write error identifies the delivery as captured live but unsaved.
- [x] **Report failed clears.** Surface failures from `Store.Clear` and update the visible history only after a successful clear. Done when an injected error keeps the visible history and explains the failure.

## 2. Prepare the GitHub release

- [x] **Build a repeatable release candidate.** Pin compatible Go and GoReleaser versions, keep cross-repo Homebrew and Scoop publication independent, and run a snapshot. Done when the build yields Windows, macOS, and Linux archives with SHA-256 checksums without requiring credentials for package repositories. [GoReleaser publishing permissions](https://goreleaser.com/resources/errors/resource-not-accessible-by-integration/)
- [x] **Write a local quickstart.** Provide a copyable shell example and a PowerShell example using a test payload and an isolated data directory. Done when a clean install can capture, inspect, and replay a request to a disposable local handler.
- [x] **Write a Stripe CLI recipe.** Connect the provider CLI to Hookline and use a test-only secret with a local receiver. Done when a user can capture an event, restart Hookline, edit the saved payload, and see Stripe’s official verifier accept the replay. Check that the receiver got the expected path and query.
- [x] **Write a GitHub webhook recipe.** Use a test repository and an existing tunnel. Document the ngrok port overlap, how the replay target combines with the captured path, and how capture mode acknowledges requests. Done when a user can receive and replay a delivery using only the instructions. [ngrok’s local inspector](https://ngrok.com/docs/gateway/agent/web-inspection-interface)
- [x] **Record a short demo.** Update the existing VHS tape or record the walkthrough with test data. Done when the README preview shows a capture, a visible edit, and a successful replay response.
- [ ] **Verify the release candidate.** Run tests, `go vet`, and the CI race suite. Smoke-test the archives on Windows, macOS, and Linux, and run the signed Stripe walkthrough from a candidate binary. Done when the results are recorded for the candidate commit.
- [ ] **Publish and verify the GitHub release.** Tag the verified commit and publish the archives, checksums, and release notes. Done when the downloaded binary and `go install …@latest` report the intended release and expose the documented signing option.

## 3. Validate repeat use

- [ ] **Recruit five developers with active webhook work.** Include developers who already use Stripe CLI, ngrok, or cURL. Done when each participant has a real integration task or a delivery they want to reproduce.
- [ ] **Run a two-week pilot.** Record the participant’s current workflow, install time, time to first capture, time from capture to replay, and where they switch back to another tool. Done when each session has an outcome and a concrete reason for any fallback.
- [ ] **Check for repeat use.** Follow up about a second debugging session or a saved regression test. Done when the results record whether at least three participants reproduced a real issue and at least two reused Hookline or kept a test. Treat the counts as directional evidence.
- [ ] **Choose one follow-up based on the pilot.** Favor fixture replay when users want to retain cases. Favor opt-in capture-and-forward when users repeatedly need traffic to reach their app immediately. If users return to existing tools, investigate their reasons before expanding the scope. Done when the next decision names the evidence behind it.

## 4. Build the fixture workflow if the pilot supports it

- [ ] **Add a synthetic regression fixture.** Use a realistic webhook shape, test-only credentials, an isolated test database, and stubbed downstream calls. Done when running the fixture cannot trigger real billing, email, or other external effects.
- [ ] **Add one non-interactive fixture replay command.** Require an explicit fixture and loopback destination. Re-sign at send time with a test secret when needed. Use a timeout, bounded output, and predictable exit codes. Done when the same command runs without a terminal prompt and fails clearly on an unexpected result.
- [ ] **Automate the regression in GitHub Actions.** Start the test receiver on the same runner and assert its behavior after replay. Done when the example fails with the original handler bug and passes with the fix, using the same fixture and command.
- [ ] **Try the same case with a local coding agent.** Give the agent the synthetic fixture, let it reproduce the failure, and reuse the exact command for verification. Compare the effort with plain cURL and a checked-in payload. Done when the trial records where Hookline saves work and what output is exposed to the agent. Treat webhook text as untrusted data. A local tool’s output can still enter a hosted model’s context.
- [ ] **Add reviewed fixture export if users repeatedly save captures.** Produce a separate, versioned fixture the user can inspect before sharing. Exclude sensitive headers by default and make body values reviewable. Done when a user can safely turn a chosen capture into a test without modifying the original record.
- [ ] **Add scripted inspection if users need programmatic selection.** Start with bounded, metadata-first JSON and stable delivery IDs. Done when a script can select a capture without scraping the TUI or reading full bodies by default.
- [ ] **Evaluate MCP if users can name a workflow the CLI handles poorly.** Define a local, read-only interface for that workflow. Done when a small prototype demonstrates a clear improvement with an explicit data boundary, or the evaluation records why the CLI is sufficient.

## 5. Prototype live forwarding if the pilot supports it

- [ ] **Test opt-in local forwarding.** Use an existing ingress route, preserve the incoming body bytes, and make the response behavior explicit. Done when the developer can inspect the same delivery their local handler received and see the handler’s response.
- [ ] **Retest with developers who hit the ingress or forwarding blocker.** Done when those developers can complete the workflow and report whether it replaces their existing setup.

## 6. Revisit distribution after the GitHub release

- [ ] **Review installation friction from the pilot.** Record operating systems, how participants installed Hookline, and where installation failed or required extra setup. Done when there is enough evidence to choose whether an additional channel is worth maintaining.
- [ ] **Choose a package channel if it solves observed friction.** Compare npm, Homebrew, and Scoop against users’ existing tooling, platform coverage, and maintenance cost. Done when the decision records the audience and expected benefit. GitHub binaries can remain the only maintained channel if they meet the need.
- [ ] **Publish to the chosen package channel if one is selected.** Distribute the same version as the GitHub release. Done when install and upgrade work on the supported platforms and the package reports the correct version.
- [ ] **List Hookline where terminal users discover tools.** Use the verified GitHub release and demo to prepare a Terminal Trove submission once the walkthrough works for new users. Done when the listing points to the maintained release. [Terminal Trove submission criteria](https://terminaltrove.com/submit/)
